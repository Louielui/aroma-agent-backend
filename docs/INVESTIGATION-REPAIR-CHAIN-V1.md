# Read-only repair evidence chain v1

The question "Why did the previous development task fail; is it fixed now?"
must distinguish an exact failed work record from another successful task.

The existing Owner operational reader now projects a host-issued registered
task ID from the structured recipe identifier. This joins task → candidate →
adoption by exact identities, including bounded transitive links. Shared titles,
dates and a shared task parent alone cannot prove a repair of a different work.
The bounded sample retains those exact links before unrelated recent records.

Each investigation saves an independently graded chain:

1. Original failure record.
2. Explicitly linked follow-up work.
3. Complete passing historical test receipt for that work.
4. Historical adoption receipt.
5. Adoption commit, fresh loaded revision and current registered-file agreement.
6. Failing baseline and passing candidate using the same protected test package
   and sandbox source/dependency input hashes, matching the adopted inputs.
7. Verification of the original failure on the live application path.

The Owner brief states the first missing step in plain language; detailed stages
and exact source references are retained under the investigation evidence.
Source unavailability and contradictory loaded revisions are distinguished from
unknown evidence. Old, absent and conflicting current-version observations fail
closed. A later successful adoption of the exact same operation can confirm
recovery of its prerequisite, not repair of every product defect.

Sandbox hash witnesses are projected only from the fixed host result envelope:
engine, boundary checks, full input-hash equality and evidence hash. Worker
stdout, source/test bodies, credentials and sandbox paths are not exposed.
Counters alone do not establish matching protected tests. A failing baseline
and passing candidate that match the loaded source support **only the registered
source acceptance scope**; they do not prove the live application path repaired.
The final repaired facet remains unknown without that separate measurement.

This delivery adds no write permission, dispatch adapter or automatic replay.
Investigation neither runs tests nor edits/adopts code nor restarts services.
Existing historical records are not rewritten to invent links or test proof.
Live-path regression collection, provider billing and complete external-worker
inventory remain separate gaps. The architecture component stays partial.

Validation includes envelope tampering, exact/transitive identity joins, unrelated
success rejection, skipped tests, changed inputs/protected tests, source drift,
old/missing boot receipts, contradictory versions, unavailable records and
Chinese/English intake through the real investigation composition with bounded
connector fixtures. These tests do not substitute for real subscription acceptance.

Measured pre-delivery validation on 2026-10-08: 387 focused tests passed. The
complete src/scripts/test suite passed 7,132 tests, with zero failures or
cancellations and five existing skips. No machine checks were excluded.
Real subscription reports and loaded-version checks are recorded separately
in the delivery workspace rather than inferred from these controlled tests.
