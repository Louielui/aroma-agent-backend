# Owner goal integrity V1 — offline candidate

The motivating procurement request requires a daily 08:00 schedule, complete
supplier lists and a Costco cart without checkout. Returning order suggestions
alone cannot complete that objective. This candidate connects reporting metadata
to the existing Goal Decomposer, intake, stores and Action Gateway. It adds no
agent framework, executor, schedule, browser action or permission grant.

## Shared contract and admission

The optional ownerGoal contract retains the exact original objective, request ID,
mandatory outcomes and steps, required capabilities, authorization requirements,
status, completion evidence, blockers and limitations. grantsAuthority is always
false. Version and catalogue/target scope hashes bind each goal to its request.

Host segmentation retains every mandatory Owner clause. Only a whole closed
no-checkout/no-payment prohibition is excluded from outcomes and retained as a
constraint. Unknown negatives stay mandatory. Excessive fragmentation retains
one unresolved full objective instead of truncating the request. Chinese
transition words split only before an action prefix, so an after-insertion
question is not mistaken for an independent cart command.

Admission reuses existing routing and bounded business-action grammar per clause.
A question in one information step cannot erase another explicit action clause.
An explicit schedule object may include relative information such as which items
to order. Analytic objects and ordinary status/impact questions retain the
informational path. The legacy business branch additionally requires a business
effect at the command head; procurement nouns inside analysis are insufficient.
The Chinese scheduler fallback requires a complete imperative, excluding
noun-phrase continuations about benefits, steps or what happens afterwards. Concrete cart insertion must end at the cart target or a
closed no-checkout qualifier; explanations and hypotheticals remain information.

Bounded polite prefixes and qualifiers, including please/just/also and Chinese
object-fronted forms, affect recognition only. Exact Owner text is never rewritten
in the contract. The same normalization recognizes one exact supported scheduler
effect for reporting evidence; it does not bypass proposal creation or approval.
This is not a universal semantic intent recognizer. Ambiguous or unsupported
language may require clarification.

The existing single Goal Decomposer call may label exact host-derived clauses
with registered capabilities. It cannot remove outcomes, invent tools, or turn
source material/history/model prose into Owner instructions or authority. Its
Owner mappings survive a refused read-fact plan. Legacy plans default to no new
mappings. Model mappings cannot promote an informational turn into an action goal.

## Persistence and independent goals

The existing Conversation Store keeps optional ownerGoals and activeOwnerGoalId
reporting metadata. New business requests, bound or unbound, retain their complete
objective while earlier independent unresolved goals remain indexed and visible.
Ordinary topics cannot erase the index. The cursor selects a report, not authority.
No capabilities, approvals, execution bindings or action contexts are combined
between goals. Corrupt canonical history is not overwritten.

The existing Task Store accepts host goal metadata and adds a separate goalStatus;
legacy task state remains unchanged. Investigation completed still means that its
read-only handler finished. It does not establish business-goal completion.
A same-conversation status request reads saved reporting state without a new
model call, source access, execution, or permission renewal.

Closed acknowledgements use the no-model status shortcut only immediately after
an unresolved goal report without a planning offer/context. A persistent completed
cursor cannot swallow acceptance of an unrelated offer. Pure acknowledgements and
permission questions retain the prior goal. New compound requests on refusal,
clarification, unsupported, approval-interpretation and duplicate-proposal paths
retain their own full unbound objective and grant no execution authority.

## Completion evidence and existing Action Gateway

GOAL_COMPLETED requires host-verified complete evidence for every mandatory
outcome, with matching goal, outcome, capability and current scope. A source
read alone proves neither an action nor a complete business outcome. Missing,
revoked or incomplete read coverage remains visible. One verified child yields
partial progress while other outcomes remain unresolved.

For the existing scheduler pause/resume gateway, reporting binds only an exact
supported target/effect clause to the host-prepared proposal ID/hash and context.
Only an authenticated verified host run with matching definition hash, desired
state, idle readback and verified timeline can complete that clause. It cannot
complete an attached cart operation. The generic evidence helper requires a
trusted host verifier and is not exposed as a model/client tool.

RPC/button and typed confirmations synchronize exact matching canonical goals,
independently of the active cursor. Their host-only refresh pins immutable
objective, scope, steps, capability, authorization and execution-binding fields.
It neither replays execution nor invents an Owner turn. Reporting snapshots are
re-read after asynchronous gateway calls before synchronous rendering/saving, so
a concurrent verified receipt cannot be overwritten with old pending evidence.

The existing proposal shape, display requirement, hash/nonce, approval, expiry,
cancellation and recovery rules remain unchanged. Each inverse still needs its
own approval. A new inverse goal requires an actual bound host inverse and a
fully completed prior whole goal. Restoring one child of a partial compound goal
retains every unresolved outcome; free-form unbound inverses retain the prior
goal rather than erase it. Conversation errors release the existing turn lock.

Tracking failure is separate from an action result. A failed refresh reports a
warning and omits stale goal metadata while preserving the proposal-context
transcript. A preparation receipt becomes completed only after that context is
saved; an unsaved proposal cannot become a successful replay-only response.
A later authenticated readback may recover evidence without repeating the effect.
After an answer exists, pending-history lookup or append errors preserve the
canonical reply, show the tracking warning, and retain it in any successfully
saved transcript. A failed status append also warns. These replies grant nothing.

## Answer integrity

Owner instructions have an attributed ownerInstructions channel containing exact
quotes from the current message. Dates, times, quantities and constraints remain
Owner text, never external business evidence or proof of execution. Numeric,
name, source and completeness checks for external facts remain unchanged. Source
or history quotes cannot enter this channel. Old answer plans default to empty.

For admitted action goals, the host composes progress and all unresolved outcomes.
Arbitrary model action-completion prose is excluded from visible/archive replies
and ancillary judgment/reasons/offer/next-step fields. Deterministic retrieved
rows and source limitations reuse the existing read formatter. Host clarification,
structured proposal and recommendation outcomes reuse their existing grounded
renderers. Model mode/reply/offer alone cannot establish those host outcomes.

## Verification scope and remaining limits

Offline regressions use the literal failed procurement request, independent
informational and imperative variants, actual existing intake/HTTP/gateway code,
isolated stores and fake schedulers/providers. They exercise complete objective
preservation, recurrence/time, missing capability, partial versus verified
completion, typed instructions, legacy tasks, stale scopes, injection, proposal
approval/readback, persistence failures and concurrent evidence updates.
Fixtures are not authenticated company-data acceptance or deployed UI evidence.

No new scheduling, browser, Costco, checkout, unattended permission or business
database operation is enabled. Existing tasks are not migrated or granted new
permissions. Unsupported or ambiguous outcomes stay unverified; future business
outcome types require their own registered host evidence verifier. No live-source
or deployment acceptance is claimed by this candidate.
