# Controlled repair v1

Owner scope: local Xiangxiang only. This chapter connects diagnosis → actual
regression reproduction → reviewable fixed plan → one-use Owner approval →
Codex selection → isolated host recipe application → independent immutable
tests → exact change evidence and terminal memory receipt.

The first catalogue contains the three findings from diagnosis
`61f06cfc-6521-4a1f-8586-21aabcf37c0f`, source commit
`2b5b2ea0dd16582e1768c8ad0cb6bb681abcdb58`. Fifteen exact reviewed committed
source/dependency blobs enter the disposable copy. Only four source files change.
The original snapshot is explicitly historical; the live HEAD/boot identifier is
separate, read before preparation, approval and acceptance. It is not a claim that
the whole current application has been audited. The default-directory defect is
latent: live composition already supplied independent directories.

The seven host checks reproduce six baseline failures. They cover cancellation
and timeout single terminal outcome/receipt, default-directory collision,
missing and thrown cost telemetry, numeric averages ignoring unknown observations,
and an unchanged invalid-workflow control. Tests and support sources are immutable.
After recipe application, all seven must pass with no skips or cancellation.
File content/hashes and extra files are independently rechecked.

Existing Capability Registry, high-risk Policy rule, Dispatcher, Owner gate,
single-use hash-bound approval store and atomic run store are reused. Preparation
does not call a model. Approval expires after ten minutes, is consumed once, and
binds work order, diagnosis, original source, live revision, tests and baseline.
Restart invalidates pending approvals and marks active jobs interrupted; no
automatic replay or retry. Foreign origins, extra fields, arbitrary paths/models/
shell commands, production scope and API fallback have no surface.

The live worker is latest Sol `gpt-6.1-sol`, medium, existing subscription and
Owner-authorized available credits under the unchanged account controls. Worker
output is a bounded enum decision and explanation. Executable bytes come only
from host-reviewed templates guarded by exact preimage hashes. Arbitrary model
code is never executed.

**Observed limitation:** Windows app-server command execution plus Node permission
checks denied out-of-scope reads/writes, child processes and worker threads, but
a real loopback network canary connection succeeded even with networkAccess false.
No network-isolation claim is made. This is why v1 permits only the reviewed
catalogue. Arbitrary edits and execution of model-supplied code remain unconnected.
Node permissions and a cleaned environment bound the reviewed fixture execution;
the source and templates contain no live business/network operation in these checks.

Owner page `/code-repair` links from diagnosis and architecture. It shows baseline,
scope, approval hash, worker, actual after-tests, before/after content/hash, stages,
and queued/saved/unavailable receipt honestly. Source code stays in Owner job files;
the canonical memory event is a compact terminal receipt, not raw source. Queued
does not mean semantic indexing is finished. All job files and workspaces are
retained for review. Completion means an accepted isolated artifact, not adoption.

Unconnected: arbitrary code repair, network-isolated model-code execution, Claude
repair/review, other projects and automatic application to the running backend.
An accepted change package still needs a separate reviewed adoption/release.
Normal memory processing/backups and the Owner-paused acceptance automation remain
unchanged. No production restaurant writes, email sends, credit purchases or remote
Git pushes are part of this chapter.
