# Bounded work results and actual coding-thread visibility

This extends the existing Project Work, Bridge, usage budget and read-only
progress reader. It adds no agent loop, provider credential or execution lane.
Candidate implementation and isolated evidence do not establish deployment or
Codex desktop visibility. Preserve the exact-commit Owner promotion gates.

## Actual Codex thread binding

Only Owner-approved registered repository coding with the existing usage root and
owner_deployment_package_required delivery can request a persistent worker thread.
The client uses its existing ChatGPT subscription RPC and the original metered
turn. Model/effort, read-only sandbox, disabled shell/tools/MCPs, clean environment,
source verification and pre-send budget enforcement remain in place. Normal chat
and unrelated workloads remain ephemeral.

Before sending that turn, the host saves the actual provider thread id in the
same work record. Failed durable binding prevents the model turn. A later
source-authorized coding continuation resumes that same thread; it cannot choose
an unrelated chat from browser input. The binding is not an approval to resume a
task, expand scope, execute tools, merge or deploy. Existing original roots cannot
gain capacity by retaining or resuming a thread.

The existing Bridge forwards canonical work-stage events to a metadata-only title
publisher. It never creates a second thread, starts a model turn or runs a timer.
Title updates coalesce per work and reject older events. Exact acknowledgement,
unknown delivery and failure receipts use the existing Action store under the
worker root's project-thread-progress folder. They do not overwrite work records
or enqueue memory indexing. Recovery events retain the same memory exclusion.
The final title distinguishes a prepared candidate from a deployed change.

Thread ids are recorded facts. Desktop visibility is explicitly not_verified
until an independent App read/visible-screen check confirms the real metered
worker's conversation. Thread storage, title acknowledgements and a protocol
fixture alone do not establish a visible task or completed workflow.
