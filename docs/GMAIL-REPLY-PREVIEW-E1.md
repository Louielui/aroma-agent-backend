# Browser-aware Gmail reply preview E1

The normal Chrome sidepanel composer recognizes a deictic email reply request in automatic context mode. A fresh V3 task preserves the original Owner Goal, displays the exact mailbox/message/thread read scope and obtains the existing task consent. Toolbar Grant is still required. Browser contents are evidence, never instructions or authorization.

The collector requires exactly one visible expanded Gmail message with hexadecimal legacy message/thread attributes and a visible account identity marker. It does not derive API IDs from the subject or decode opaque URL fragments. The route token only detects navigation. Current tab/window/document/content and locator are rechecked before dispatch; navigation cancels in-flight work. Unsupported or ambiguous layouts fail closed.

The existing Gmail scope lease, provider-sharing policy and read-only ToolGateway verify the configured mailbox, credential/source revision, actual OAuth scopes, Gmail profile, selected API message and exact API thread membership. A new fixed `get` resource can read that thread only. No OAuth consent, external permission, Action Gateway action or Gmail write method was added. V1/V2 tasks cannot inherit this capability.

Reads retain at most eight messages, including the selected parent, and 4,000 body characters per message. The SDK response limit remains 1 MiB. Attachments are excluded. Truncated, attachment-bearing, omitted or unavailable content is explicitly incomplete. Missing required reply headers stops preview generation rather than guessing identity. Sender, Reply-To, original To/Cc, Message-ID, References and In-Reply-To are retained in verified context. The host fixes displayed recipient and subject; model text supplies only the preview body or a clarification question.

The U1 shadow generator receives the thread as untrusted data, with tool access disabled by the existing adapter. The result explicitly states that no Gmail draft was saved and no message sent. Reading or previewing does not complete the Owner's broader reply goal. Cancellation, source revision checks and saved-result retrieval preserve existing recovery behavior. Source audit events contain operations and coverage, not email bodies or headers. Owner-facing previews use the existing task-result persistence and retention boundary.

Offline tests exercise synthetic connector-to-preview execution and an isolated actual Edge sidepanel/collector. They do not access an authenticated browser, mailbox, business database or production service. Independent exact-commit review and full isolated suite receipts are required before promotion.

Native Host packaging: the pure Gmail locator validator is defined in the already packaged Browser contract. The Backend Gmail contract reuses it and keeps intent routing on the Backend. The flat installation layout, pinned file list, installer and permissions remain unchanged. The installation regression executes the actual PrepareOnly installer body against a temporary Git fixture, rebinding only repository, output and Node paths in its test copy. It compiles both native executables and checks package hashes. Module loading runs from that package with NODE_PATH removed. The real packaged Browser worker then crosses the compiled launcher/native broker to a synthetic Backend; only credential acquisition and the fixed HTTP destination are replaced by test fixtures. No real User token is read and no request reaches the production Backend. Missing pinned and transitive dependencies are negative controls. The existing backend-only lazy Express export in clientUpdate is not invoked by the Native Host.

Remaining limits: Gmail DOM variants, multiple expanded messages and missing account markers are unsupported. The main application has no ambient Chrome context; E1 applies to the ordinary sidepanel conversation. Browser consent remains explicit, and text-only previews may require Owner clarification. Prompt rules reduce malicious-content influence; host boundaries prevent writes and recipient/tool selection regardless of model output, but do not prove semantic correctness of every generated sentence.

Controlled live acceptance requires separate Owner approval, an unchanged reviewed tree, an authorized test mailbox/thread, Toolbar Grant and task consent. Verify exact account/message/thread, headers, contextual body, incomplete-context disclosure, tab-switch cancellation, revoked access, reload without replay and zero draft/send operations. Do not activate draft saving or sending as part of E1.
