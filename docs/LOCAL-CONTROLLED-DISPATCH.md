# Local understanding and controlled Codex App work

This candidate keeps Qwen3.5 9B as Xiangxiang's chat, planning and memory brain.
An explicitly authorized repository task may use the existing ChatGPT and Claude
subscriptions. This is a separate execution grant, never a model fallback.
Installation creates no task, inference allowance, thread, scope approval or
deployment authorization. Existing paused ledgers and memory settings are untouched.

## Existing components reused

The authenticated backend forwards a closed Project Tasks / Project Work contract
to the Owner bridge's fixed loopback `/controlled-dispatch` endpoint. The deployed
source profile selects `owner_scoped_subscription`; a host `off` override remains
off. No user message, website, model reply or request body can change this profile.
The bridge checks its boot commit, existing worker authorization matrix and fixed
`Documents/ChatGPT/香香派工` project directory. Health is metadata only and reports
App visibility as unverified. A failed, stale or differently versioned probe cannot
advertise the connection as ready.

Existing Owner authentication, same-origin JSON routes, source inventory/hash,
Policy, nonce approval, Action Store locks, durable repository usage budget,
isolated worker and canonical result presentation remain authoritative. General
requests preserve the full goal and reuse matching work IDs. They do not run a
model. Old unbounded fixed recipes, adoption, arbitrary command/provider proxies,
website operations and `/complete` are not exposed by this connector.

## Approval and execution sequence

1. Request or explicitly continue the original work ID. Select eligible committed
   source, editable files, read-only dependencies and acceptance criteria.
2. Owner approves the displayed scope/hash and existing eight-helper allowance.
   A fresh test-drafting call then creates a real persistent Codex provider thread
   in the existing App project. Failed tests or reviews retain their evidence and
   consume the same allowance; a rejected draft resumes that thread.
3. Independently reviewed test draft requires its own Owner approval. Preparation
   of coding seals the original provider-thread identity with the source and work
   order. A changed identity invalidates the coding approval. Renewal cannot change
   the sealed thread or reset the allowance.
4. Separate coding approval resumes the same thread for the existing isolated
   worker. Progress titles distinguish test approval, coding, review, failure and
   candidate completion. They never call a candidate deployed. Title-publishing
   failure remains an unavailable receipt, not task success.
5. Canonical stored results return to Xiangxiang through the existing GET/polling
   interface. Before/after, tests, baseline and review evidence use existing
   patch-hash verification. Completion is held for an Owner deployment package;
   no automatic merge, installation or business write follows a worker result.

Before inference authorization, automatic memory must already be paused and idle;
unknown state or another active workflow refuses execution. This connector never
changes that setting. Subscription login, available model and quota are checked by
the existing native client. API keys and purchased-credit fallback remain refused.
No recovery allowance is issued here; same-ID recovery retains existing approval,
source, budget, restart and replay protections. No automatic restart resumption.

The existing acquisition-only lock wait now defaults to its already supported
one-second ceiling instead of 250ms. Real 400ms holders previously caused a
pre-send `usage_busy` failure. Only acquisition is retried; no loaded mutation,
evidence callback, reservation or provider send is replayed. Permanent contention
and filesystem/audit failures still stop. Cap values and all historical profiles
are unchanged. The failed full suite and its WSL transport-timeout evidence are
retained separately; a later PASS never relabels that run.
Two legacy live security-test files also serialize their use of the shared WSL
clone host through a test-only resource gate. All original assertions, real
distro calls and native deadlines remain unchanged. No production WSL runner,
Git configuration, credential, source authority or intentional in-test parallel
budget request is changed. The gate refuses unknown owners and never deletes a
changed lock. Parallel OS-process tests verify the test-resource isolation.

## Local/cloud boundary

The local process can POST only the closed control contract and canonical memory
storage to the authenticated bridge. Chat completion, public search, arbitrary
endpoints, external AI URLs and Codex child execution inside that process remain
blocked. The separate Owner bridge performs only explicitly approved subscription
work. Gmail and other business actions gain no new access. Memory extraction,
reflection and local inference do not acquire cloud fallback.

## Verification and remaining host gate

Offline integration uses temporary repositories, real existing durable budgets,
authenticated loopback HTTP and deterministic provider/RPC fixtures. It covers
scope/approval denial, deduplication, source/thread tampering, restart, retries,
shared cap exhaustion before send, canonical result return, held deployment and
unchanged source. These tests do not establish real subscription entitlement,
Codex App pixels, live provider behavior or production installation.

After a separately approved exact-SHA deployment, first perform zero-model host
checks: source/tree/launcher, four host checks, local model and cloud fence,
authenticated status with matching boot SHA, fixed project path, memory pause and
all paused ledger hashes. Only a later separately approved bounded work order may
prove real App visibility, progress and result return. Record the canonical work
ID, actual provider thread ID, native reservations/sends, terminal status, verified
candidate, tests/review evidence and actual App view. Stop on failure; do not replay
or create replacement allowance.

The implementation follows the official persistent thread/start, thread/resume,
turn/start and terminal turn/completed contract:
https://learn.chatgpt.com/docs/app-server . It does not invent an App message
injection method or treat model/list as proof of entitlement.

Rollback requires a separate approved exact local source (pre-candidate local
baseline), preserves private launcher bytes and all task/failure/budget records,
and never restores production memory or a cloud-brain version.
