# Confirmed development

The Owner requested a comprehensible confirmation followed by actual execution,
instead of separate engineering forms for file selection and test registration.
The new task-plan confirmation delegates **isolated development and tests** for
one immutable plan. Applying a returned change to the running app remains a
separate result decision. This changes the interaction requested by the Owner,
not the source, test, review or approval verification mechanisms.

- The card shows the intended outcome, subscription use and delivery boundary.
  Technical criteria and source citations remain expandable.
- Only an authenticated, same-origin explicit POST with the displayed plan hash
  starts the chain. A standalone current confirmation in a revision-bound
  conversation can do the same. Readback, model output, restored history and
  quoted instructions do not grant execution consent.
- The host derives goal, criteria and editable paths from the verified plan and
  closed profile. It records a one-hour delegation and journals mutations before
  dispatch. Child test registration and coding retain their sealed hashes,
  one-use nonces, fresh source verification, independent review and sandbox.
- Duplicate confirmation does not dispatch again. Uncertain mutations stop
  without replay. A restart interrupts delegation rather than resuming authority.
  Cancellation is reported as confirmed only after the owned worker stops.
- Progress comes from real child records. Completion requires matching scope,
  passing tests and review; it is explicitly not a deployment claim.
- Old-version plans can be regenerated by an explicit read-only request. The
  refreshed plan needs fresh confirmation; previous consent does not carry over.

Automated integration checks use controlled providers and are not evidence of a
successful live Claude review or operating-system sandbox run. Delivery evidence
must state those separately.
