# Development proposal v1

The Owner can ask “香香，檢查目前開發進度，提出下一項修正方案。” or open `/development-plan` and dispatch the fixed `development-proposal-v1` recipe. Page loads and status reads do not invoke a model. This is a proposal over public development metadata, not source-code diagnosis or an implementation worker.

The narrow `DevelopmentProposal@1` contract uses the existing capability registry, policy and dispatcher. One Codex subscription adapter is registered for this contract; an unexpected second manifest refuses dispatch. No fallback, paid API, automatic retry, arbitrary input prompt, project path, credential, command or write tool is exposed. The existing subscription text client disables shell, file edits, MCP, apps, plugins and delegation, uses isolated ephemeral threads and checks real ChatGPT account/model/quota before completion.

Before context or model work, the subscription preflight must pass. The Owner-only Live Context reader refreshes the configured public repository, remote checks and local deployed/boot revision identifiers. A field allowlist bounds the packet to 40 public metadata rows; PR bodies and private/business data are not included. Remote test evidence is pinned to its remote SHA, never presented as a local deployed test result. Source text is untrusted and cannot drive routing.

After completion, the host validates the exact bounded output shape and evidence IDs, re-reads sources without the UI cache, and compares the packet hash and revisions. A mismatch withholds the proposal. Matching source evidence does not prove the model's rationale: the UI labels the recommendation as an unverified worker proposal, not execution or measured acceptance. No files have changed and no tests have run through this recipe.

Work orders use the existing atomic run store in its own `development-plan-runs` directory. They record scope, requester, source hash, policy/dispatch milestones and terminal status. Persisted request IDs prevent repeated subscription calls. Active records are interrupted on reconstruction without replay; cancellation and timeout abort the loopback request and discard late output. Any failed audit write stops subsequent work. Only a compact measured terminal receipt enters Owner episodic memory; the result is not a verified decision or procedural memory.

Acceptance currently covers deterministic routing, policy order, quota refusal, source validation/change, bounds, idempotency, cancellation, timeout, restart reconstruction, Owner/origin protection, chat links and durable storage. The Owner may explicitly allow existing ChatGPT credits when included quota is exhausted; the same subscription transport checks actual credits and spending caps, without API fallback or automatic replay. Real successful proposals and post-worker source verification are evidenced by the work orders rather than inferred from quota eligibility. General routing, Claude architecture/review dispatch, repository source access, patches, approvals for applying changes and all external writes remain outside v1.
